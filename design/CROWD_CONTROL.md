# CROWD 機能 設計(GPTレビュー反映版)

日付: 2026-08-25 / 状態: **実装済み・実機未確認**
レビュー: GPT(Codex) 設計レビュー1周実施。指摘は下の「レビューで変えたこと」に反映済み。

実装の現在地は末尾の §13。**サーバ側は手元でテスト済み、C++側はコンパイルが通っただけ**で、
画面に出したところは誰も見ていない。

観客が自分のスマホで連打 → ゲージが溜まる → 溜まり具合が常時じわじわ効く +
満タンで一発大きいのが来る。

決定済みの前提(本人判断 2026-08-25):
- 満タン時は **両方乗せ**(常時じわじわ + 満タンで一発)
- 想定人数 **数人〜20人**(小さいハコ / 身内)

## 1. なぜ「つまみ」ではなく「連打ゲージ」か

つまみを観客に開放すると、値が1つしかないので**誰かの入力が誰かの入力を消す**。
100人いても実質1人しか操作していない。連打は**足し算**なので全員分そのまま乗る。

副次的な利点:
- 通信が軽い。値を送り続けるのではなく「直近250msに何回押したか」の整数1個で済む
- 荒らしが効かない。1端末あたりの上限を決めれば、連打ツール = 熱心な人1人分
- 画面にゲージを出せば「押す→溜まる→壊れる」が見えるので、勝手に加速する

## 2. 構成

**ミキサー本体に web サーバを埋め込まない。別プロセスにする。**

理由: ミキサーは C++ / Windows でビルドが重い。スマホ画面の文言を1つ直すたびに
再ビルドは非現実的。加えて、HTTP/WebSocket・不正入力・例外を**描画プロセスに
持ち込まない**という安全上の意味がある(ライブ中に描画が落ちるのが最悪)。

```
[観客スマホ] --POST(250ms)--> [crowd-server (Node)] --UDP 20B--> [vj-mix-spike1.exe]
      ^      <--SSE(10Hz)---        |                <--UDP 8B---        |
      |  連打数を送る / ゲージを受け取る | /vj 調整ページ                      v
      +---- QR画像で参加              | (localhost + トークン)        出力画面にゲージ描画
```

**WebSocket をやめて POST + SSE にした。** どちらも Node に最初から入っているので
**npm install が要らない**。20人×毎秒4回の POST は 80回/秒で、まったく余裕がある。
本番当日に「npm install が通らない」で詰まる可能性を消す方が価値が大きい。

**「Node 1ファイルだから簡単」は嘘。** 実際には Node の導入、起動順、IPの確認、
Windows ファイアウォールの許可、ログ、落ちた時の再起動が要る。
→ **起動用の .bat を必ず用意する**(エミュ2台+ミキサーの既存 bat に足す)。

### スマホ ⇄ サーバ
- 上り: `POST /tap` に 250msごと `{id, taps}`。**サーバはこの申告値を信用しない**(下記)
- 下り: `GET /events`(SSE)で 10Hz、`{charge, burst, cooldown, active, held, ...}`。
  スマホにもゲージとクールダウンを出すため下り経路は必須
- スマホがバックグラウンドに回る時は `sendBeacon` で溜まった分を吐く
  (ポケットに入れた瞬間に最後の0.25秒が消えるのを防ぐ)

### サーバ → ミキサー(UDP 127.0.0.1:8778)
- 20Hz。**20バイト固定**を1フィールドずつ明示的に組み立てる(構造体をそのまま投げない):

| offset | 型 | 中身 |
|---|---|---|
| 0 | u32 | magic `VJCR` |
| 4 | u8 | version = 1 |
| 5 | u8 | flags: bit0 満タン待機 / bit1 HOLD中 / bit2 受付中 / bit3 クールダウン中 |
| 6 | u16 | seq |
| 8 | f32 | charge 0..1 |
| 12 | f32 | burst 0..1 |
| 16 | u16 | 押している人数 |
| 18 | u16 | クールダウン残り(1/100秒) |

逆方向(ミキサー → サーバ、127.0.0.1:8779)は8バイト: magic `VJCC` / version / flags / seq。
10Hz で HOLD と参加受付を送る。
- 受信側は**キューを空になるまで読み、最新 seq だけ採用**する。
  seq が逆行したパケットは捨てる(古い値に巻き戻らないように)
- NaN / Inf / 範囲外 / 長さ違い / magic 不一致 / version 違い / seq逆行は**全部捨てる**
- **400ms 無通信で減衰開始、1秒で0へ**。サーバが死んでもミキサーは普通に動く
- 受信用と送信用で**ソケットを分ける**。Windowsでは、閉じたポートへ送った後の
  ICMP到達不能で**同じソケットの受信が WSAECONNRESET で壊れる**ため
  (`SIO_UDP_CONNRESET` も併せて無効化する)

### /vj 調整ページ
LANに開くと**観客も操作できてしまう**。localhost からのみ、かつ起動時に生成する
ランダムトークン必須。トークンはサーバのコンソールに出す。

## 3. ゲージの計算(全部サーバ側 = ビルド無しで調整可能)

各端末に**トークンバケツ**: 容量5、毎秒5補充(= 平均5taps/s、瞬間5まで許容)。
**サーバ側で経過時間から算出**する。クライアントの申告値は上限クリップのみに使う。
同じIPから作れる端末IDは4つまで。

```
gainPerTap = baseGain / sqrt(max(3, smoothedActive))
charge    += acceptedTaps * gainPerTap
charge    -= leakRate * dt
charge     = clamp(charge, 0, chargeCeil)

canBurst = (activeCount >= 2) and (cooldownRemaining <= 0) and (armed)
if charge >= 1.0 and canBurst:
    burst = 1.0 ; charge = 0 ; cooldownRemaining = 5.0
burst -= dt / burstDecaySec        # 既定 2.5秒で0へ
```

- `smoothedActive` = 直近10秒に押した端末数を、**5〜10秒で平滑した値**。
  生の数を使うと1人抜けた瞬間にゲージの伸びが跳ねる
- `chargeCeil` = クールダウン中は **0.3**、それ以外は 1.0。
  →「クールダウン中も溜め続けて明けた瞬間に自動再発火」を防ぎつつ、
  連打が完全に無反応(=故障に見える)にもならない
- **1人では発火しない**のは `activeCount >= 2` という明示ルールで担保する。
  正規化式から導出しようとすると成立しない(下記レビュー参照)

### 人数が増えるとどうなるか
`sqrt` で割るので、**全体の溜まる速さは人数の平方根で伸びる**。
「人が増えると会場が加速する」感覚は残り、かつ20人で一瞬で満タンになる暴走もしない。

既定値 `baseGain=0.011 / leakRate=0.04` での満タン到達時間(全員が毎秒5回叩いた場合):

| 人数 | 1 | 2 | 3 | 5 | 10 | 20 |
|---|---|---|---|---|---|---|
| 満タンまで | **到達しない** | 43秒 | 18秒 | 12秒 | 8秒 | 5秒 |

放置したゲージは25秒で空になる。実際の連打は毎秒4回程度なので、2割増しで見る。
**1人では漏れる量に勝てない**(毎秒5回でも 0.032/s に対し漏れが 0.04/s)。
つまり集団技であることが、quorum ルールとは別に算数でも担保されている。

## 4. 画面に何が起きるか

挿入位置は特定済み。`src/mixer/main.cpp` 約1676行:
```cpp
const vj::Params effective = autoMode.enabled
    ? vj::applyAutoMode(vjEffectParams, autoMode, vjFrameCounter)
    : vjEffectParams;
// ここに1行足すだけ:
// if (crowd.enabled) effective = applyCrowd(effective, crowd);
```

**単純な足し算にはしない。残りの余白に対して効かせる**:
```
amount    = cap * (levelW[X] * charge + burstW[X] * burst)
effective.X += (1 - effective.X) * amount        // 上限に張り付かない
```
理由: VJ が既に高い値にしている時、単純加算だとクランプされて観客の操作が
**何も見えなくなる**。逆に全項目が上限に張り付いて VJ のニュアンスが消える。

| param | 常時(charge) | 一発(burst) | 段階 |
|---|---|---|---|
| GEOMETRY | 0.6 | 1.0 | **MVPはここだけ** |
| COLOR | 0.5 | 0.8 | **MVPはここだけ** |
| CHANCE | 0.4 | 1.0 | 第2段階 |
| TEXTURE | 0.3 | 0.7 | 第2段階 |
| CHAOS | 0.2 | 0.8 | 第2段階 |
| MISSING | **0.0** | 0.5 | **最後に解禁を判断**。絵が消える |
| DEPTH | 0.0 | 0.5 | 同上 |
| MASTER | 触らない | 触らない | VJの権限。渡さない |

`cap` = VJ の「観客の効き具合」スライダー(既定 0.4、0で完全カット)。

## 5. 発火タイミングは VJ が握れるようにする(ARM)

**満タンになった瞬間が、曲として発火していい瞬間とは限らない。**
ブレイク直前や暗転中に勝手にドカンと来ると演出が壊れる。

- `ARM` トグル(ミキサーGUI):
  - **AUTO**: 満タンで即発火(通常)
  - **HOLD**: 満タンでも発火せず「溜まりきった」状態で待つ。VJ が離した瞬間に発火
- HOLD 中は出力ゲージが点滅する(客には「いつでも来るぞ」の期待感になる)

## 6. 参加ウィンドウ(観客の目を手元に固定しない)

**スマホを見ている間、客は映像を見ていない。**踊る・撮る行為とも競合する。
常時開放ではなく、**VJ が30秒程度の参加時間を開ける**方式を既定にする。

- `参加受付 OPEN / CLOSED` トグル。CLOSED 中のスマホ画面は「まもなく」表示
- OPEN の残り秒数をスマホと出力画面の両方に出す
- 常時開放も選べる(トグルを OPEN のままにするだけ)

## 7. VJ側の操作

**ミキサーGUI**(ここを増やすと再ビルドが必要なので最小限):
- `Crowd enabled` / `Crowd strength (cap)` / `ARM: AUTO|HOLD` / `参加受付 OPEN|CLOSED`
- 表示のみ: 実働N / charge バー / burst バー / クールダウン残 / 最終受信からの経過秒
- **即時カット**(cap=0)は必ず手の届く場所に置く

**手触りの調整は `/vj` ページ**(MVPでは4つだけ): baseGain, leakRate, cap, 緊急停止。
burstDecay や cooldown は最初は固定値でよい。

## 8. 観客に見せるゲージ

**画面にゲージが出ないとこの企画は成立しない**(自分の影響が見えない = 押さない)。

- 出力ビューポート下部に細いバー。charge を幅、burst を発光、HOLD 中は点滅
- **クールダウン中であることを必ず表示**する。「押しても反応しない理由」が要る
- VJ が消せるように `Show gauge on output` チェックボックス
- スマホページにも同じゲージ

## 9. 作らないもの(MVPの線引き)

- QRの自動生成 → **`public/qr.png` に自分で1回置けば配信する**だけにした
  (QRライブラリを足す価値がMVPには無い)
- 接続数の表示 → 実働数だけでよい
- ログイン / 名前 / ランキング
- 左右チーム分けでクロスフェードを綱引き ← **面白いが第2段階**
- 音声反応、Ableton Link、HTTPS

## 10. 実装順序(レビューで逆転させた)

**一番不確実なのは通信ではなく「画面が本当に気持ちよく変わるか」。**
ここが成立しなければ他は全部不要になるので、最初に確かめる。

1. **ミキサーにキー操作で charge / burst を手で注入**して、GEOMETRY と COLOR だけで
   効果と安全性を確認。サーバはまだ作らない
2. 減衰・クールダウン・ARM の手触りをここで詰める
3. 最小サーバ → UDP → ミキサー の**縦切り**を通す(ゲージ計算は固定値でよい)
4. スマホ1台の入力と、スマホへのゲージ返しを繋ぐ
5. 複数端末、平滑した人数正規化、トークンバケツ、参加ウィンドウ
6. 出力画面のゲージ描画、QR画像、`/vj` ページ、起動 bat
7. MISSING / DEPTH を解禁するか最後に判断

## 11. 検証設計

**成功条件**: 実機スマホ数台で連打して、①ゲージが溜まる ②溜まりに応じて画面が
変わる ③満タンで一発来る ④クールダウン後にまた溜まる ⑤サーバを殺してもミキサーが
落ちず絵も止まらない。判定は本人の目視 + サーバログ。

**間違うと痛い主張(3つ)**:
- (a) UDPをフレームループでノンブロッキング受信しても描画がカクつかない
- (b) 切断・再接続・ブラウザのバックグラウンド化で、集計が壊れたり固まったりしない
- (c) `cap` の範囲内なら画面が「見えなくなる」ことはない

**潰し方(生成経路と別経路で)**:
- (a) コードを読んで安心しない。**フレーム時間を実測**し crowd 有効/無効で比較
- (b) **性能試験はしない**(20台×5taps/s は Node には軽すぎて意味がない)。
  代わりに**壊し方**を試す: Wi-Fi切断→再接続、画面ロック、タブを裏に回す、
  ブラウザ終了、送信直前の切断(未送信タップの消失)、サーバ再起動、
  古いUDP到着、seq逆行、長さ違いパケット、NaN/Inf
- (c) `lastDrawn > 0` では**証拠にならない**(1枚だけ・極小・黒・画面外でも通る)。
  **出力フレームの非黒ピクセル率と平均輝度**を測る。
  さらに各パラメータ単体ではなく**同時最大**の組み合わせで測る(相互作用するため)
- **30分の連続稼働**も1回やる(60秒ではメモリリークやタイマーずれが出ない)

**検証できないこと**: 本物の会場Wi-Fi、本物の観客人数、iOS/Android の実機差。
複数タブは実機の代わりにならない(同じCPU・同じ回線・同じブラウザのため)。
→ **初回は身内20人以下で、失敗してもいい場で試す**。

## 12. レビューで変えたこと(記録)

GPTが潰した点:
- **「1人では絶対に満タンにできない」は元の式では成立していなかった**。
  1人でも `5 * baseGain / sqrt(3) > leakRate` なら到達できる。
  → `activeCount >= 2` という明示ルールに変更
- **人数正規化(activeCountで割る)は、人数が増えても速くならない**。
  N人 × baseGain/N = 常に一定。集団参加なのに3人でも20人でも同じ速度になっていた。
  → `sqrt` に変更し、人数で加速する感覚を残した
- 元の式は**クールダウン中も溜まり続けるので、明けた瞬間に自動再発火**する
  → クールダウン中は 0.3 で頭打ち
- 単純加算は、VJが既に高い値の時に**観客の操作が見えなくなる**
  → 残り余白に対して効かせる方式へ
- `/vj` を LAN に開くと観客が触れる → localhost + トークン
- スマホにゲージを出すと言いながら、**下り経路を設計していなかった**
- `lastDrawn > 0` は映像が見えている証拠にならない
- 負荷試験は無意味。本当の敵は切断・再接続・ファイアウォール
- 実装順序が逆。一番不確実な「気持ちよさ」を最後に回していた

GPTが足した「気づいていない前提」:
- **満タンの瞬間 ≠ 発火していい瞬間**(曲の構成) → ARM(HOLD)モードを追加
- **観客とVJの操作は単純加算できない** → 余白ブレンドへ
- **スマホを見ている間、客は映像を見ていない** → 参加ウィンドウ方式を既定に

採用しなかった案:
- 「人数正規化を完全に削除する(固定gain)」。20人に合わせると3人の日に遊べず、
  3人に合わせると20人で暴走する。ハコの規模が読めないので `sqrt` の折衷を採った

### ついでに直したこと

**`.vjr` 録画の再生でもグリッチが効くようにした。** それまでライブ入力の時しか
効かなかったので、録画を使って手触りを確かめることができなかった。

### キーボードだけで試す(サーバもスマホも要らない)

ミキサーの Controls → CROWD → `Keyboard test mode` にチェック。
**T を押し続けると溜まる / B で一発 / R でリセット。**
漏れる速さも一発の減衰もサーバの既定値と同じにしてあるので、
これで手触りを決めてから通信を繋げばよい。

### 完成レビュー(GPT)で見つかって直したこと

**実行して初めて出る類**なので、コンパイルが通っただけでは絶対に見つからなかったもの。

1. **再起動すると通信が数十分死ぬ**(最重量)。どちらの向きも「前に見た番号より新しい
   パケットしか受けない」実装だったが、再起動すると番号は0から始まる。
   → **1〜2秒以上の間が空いたら、次に届いたものを新しい基準として受け直す**
2. **一度上限に達したIPは、二度と新しい端末を登録できなくなる。**
   古い端末を掃除する時に、IPごとの枠から外し忘れていた
3. **一発の長さを0にすると、画面が壊れたまま戻らなくなる。**
   → 調整値は型だけでなく**範囲でも制限**するようにした(最小0.05秒)
4. **HOLD で待っている間にゲージが漏れて空になる。**さらに離した瞬間の漏れで
   1.0をわずかに割り、**発火しない**。→ 満タン+HOLD中は漏れを止め、
   「満タンに達した」ことを掛け金として持つようにした
5. **ノンブロッキング設定の失敗を無視していた。**失敗すると次の受信で
   **描画スレッドが永久に止まる**
6. **サーバが死んでも「HOLD中」「10人参加中」の表示が残る。**
   → 通信が生きている時だけ表示する
7. **ミキサーが死んでも観客は連打し続ける。**→ 3秒 controls が来なければ
   参加受付を閉じ、スマホに「準備中」を出す
8. 送信失敗時にスマホが再送していた → **二重加算になるので捨てる**方針に変更
   (batch id が無いため重複を検出できない)

### まだ誰も見ていないこと(★次に確かめること)

1. **画面が実際にどう壊れるか。**これが本丸。GEOMETRY と COLOR だけで気持ちいいか
2. ゲージのバーが出力画面のどこに出るか、大きさは適切か
3. スマホページが実機(iOS/Android)で期待どおり動くか。連打の取りこぼし、
   画面ロック、バックグラウンド復帰
4. 会場Wi-Fi / ファイアウォールの現実
5. 20台規模での体感(手元は同一PC上の模擬20台でしか試していない)

**GPT が挙げた「現場で必ず踏む」3点**(未対策・運用でしのぐ):
